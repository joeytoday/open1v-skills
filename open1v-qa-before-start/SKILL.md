# QA Before Start — 苏格拉底式需求澄清

在开始执行需求前，用苏格拉底六维提问法帮用户把需求想清楚。不直接给答案，而是通过高质量的追问，让用户自己发现需求中的盲区和关键决策点。

## 提问框架：六个维度

### 1. 澄清（Clarifying）
追问"你具体指的是什么"，消除模糊表述。
- 当用户说"做得更好"→ 问：更好的衡量标准是什么？
- 当用户说"常态化"→ 问：常态化具体指每天/每周/每月的什么动作？
- 当用户说"升级"→ 问：升级是指功能、体验、还是服务？

### 2. 假设（Probing Assumptions）
追问"这个结论背后隐含了哪些前提"，暴露未验证的假设。
- "你认为用户增长的主要瓶颈是什么？这个判断基于什么？"
- "这个目标假设了哪些资源或条件是到位的？"

### 3. 证据（Probing Evidence）
追问"你依据的数据/事实来自哪里"，区分事实和推测。
- "目前的数据支持这个方向吗？有哪些关键指标？"
- "有没有已验证的案例或先例？"

### 4. 视角（Questioning Viewpoints）
追问"还有谁可能持不同看法"，引入多角色思考。
- "用户会怎么看这个变化？付费用户和免费用户的感受一样吗？"
- "团队内部对此有共识吗？有没有反对意见？"

### 5. 后果（Probing Implications）
追问"如果这样做，短期和长期会带来什么结果"。
- "如果达成了这个目标，下一步会是什么？"
- "如果没有达成，最大的风险是什么？"

### 6. 反思（Questioning the Question）
追问"我们是不是在问对的问题"，退后一步审视全局。
- "这个问题本身是否就是最重要的问题？"
- "有没有更根本的问题被我们忽略了？"

## 提问比重分配策略

根据需求类型，调整各维度的提问比重：

| 需求类型 | 重点维度（各 2-3 题） | 辅助维度（各 1 题） | 可省略维度 |
|---------|---------------------|-------------------|-----------|
| 产品运营类 | 澄清、证据、后果 | 假设、视角 | — |
| 技术实现类 | 澄清、假设 | 证据、后果 | 视角 |
| 战略决策类 | 假设、视角、后果 | 澄清、证据 | — |
| 流程制度类 | 澄清、视角、后果 | 假设 | 证据 |

判断需求类型的方法：
- 包含"用户增长、转化率、留存、运营、推广"等关键词 → 产品运营类
- 包含"开发、实现、架构、性能、技术选型"等关键词 → 技术实现类
- 包含"方向、战略、投资、布局、长期"等关键词 → 战略决策类
- 包含"流程、SOP、规范、制度、分工"等关键词 → 流程制度类
- 混合型需求按最核心诉求归类

## 执行流程

### 第1步：接收需求
逐字读取用户的原始需求描述，不做任何解读或假设。

### 第2步：识别维度缺失
逐一检查六个维度，列出每个维度中缺失或模糊的信息点：
- 澄清：哪些关键名词/动词含义不明确？
- 假设：用户的结论隐含了哪些未说明的前提？
- 证据：哪些判断缺少数据支撑？
- 视角：是否只考虑了单一角色的立场？
- 后果：是否提到了成功/失败的具体影响？
- 反思：需求本身的方向是否值得质疑？

### 第3步：生成第一轮提问并创建文档
根据上方"提问比重分配策略"确定需求类型，按比重为每个维度分配问题数量，总计 10-15 题。

必须同时执行两件事：
1. 在对话中按维度分组展示问题，每组标注维度名称和提问意图
2. 使用 create_file 工具创建一个 markdown 文档，包含以下结构：
   - YAML frontmatter（参照用户工作区的 worknote 模板）
   - 原始需求引用
   - 维度缺失分析表
   - 按维度分组的问题列表（纯文本编号，不用 checkbox）
   - 每个问题后紧跟一行空的回答占位（用户直接在问题下方填写回答）
   - 空白需求澄清报告模板（待全部追问完成后填写）

文档格式示例（缩进使用四字符制表符）：
```
- **Q1**（🔍 澄清）：问题内容？
	- 
- **Q2**（🧩 假设）：问题内容？
	- 
```

文档存放路径：与需求相关的项目目录下，文件名格式为 `{项目名}-qa-before-start.md`。

对话中的展示格式：
```
### 🔍 澄清类问题（搞清楚你具体要什么）
1. ...
2. ...

### 🧩 假设类问题（检查背后的隐含前提）
3. ...
```

### 第4步：迭代追问（三轮迭代）
总共四轮对话（第一轮为初始提问，后续三轮为迭代追问），每轮迭代追问前必须先整合上一轮的问题和回答，生成一段简要的"上轮要点整合"摘要，然后再提出新的追问。

每轮追问的流程：
1. 整合上一轮的问题和回答，输出"上轮要点整合"摘要（3-5 条关键信息）
2. 基于整合结果，识别新的模糊点、矛盾或未定义概念
3. 生成 3-5 个新问题，聚焦于上一轮暴露的模糊点
4. 将追问和空白回答同步更新到文档中（回答直接跟在问题后面）

判断标准：
- **需要继续追问的信号**：用户回答引出了新的未定义概念；用户的两个回答之间存在逻辑矛盾；用户回答"大概"、"可能"、"应该"等不确定表述；某个关键决策点仍有多个方向未明确
- **可以提前结束追问的信号**：六个维度的核心问题都有了明确回答；用户的目标、范围、约束、优先级已清晰；没有发现新的逻辑矛盾或模糊点
- 即使可以提前结束，也至少完成三轮迭代追问（共四轮含初始提问），确保需求被充分挖掘

### 第5步：输出需求摘要
将所有回答整理为以下格式的结构化需求文档：

```markdown
## 需求澄清报告

### 核心目标
[一句话描述最终要达成的结果]

### 具体范围
- **包含**：[明确要做的事]
- **不包含**：[明确不做的事]

### 当前状态与数据基线
- [关键现状数据点1]
- [关键现状数据点2]

### 关键约束
- **资源约束**：[人力、预算、时间]
- **技术约束**：[平台、工具、依赖]
- **业务约束**：[合规、合同、策略]

### 优先级排序
1. [最重要的事]
2. [次重要的事]
3. ...

### 成功标准
- **核心指标**：[可量化的成功定义]
- **时间节点**：[关键里程碑]
- **验收方式**：[如何判断做完了]

### 关键假设（已验证 / 待验证）
- ✅ [已确认的假设]
- ❓ [待验证的假设]

### 待确认事项
- [ ] [用户说"不确定"或未回答的问题]
```

## 提问原则

- 每轮最多展示 15 个问题，按维度分组，避免压倒用户
- 问题之间有逻辑递进关系，由浅入深：先澄清事实，再检查假设，最后探讨后果
- 避免引导性提问，保持中立和开放——问"你怎么看"而非"你是不是觉得"
- 对用户的每个回答先表示理解（一句话复述要点），再继续追问
- 用户说"不确定"或"还没想好"时，标记为待确认项，不继续追问该点
- 用选择题降低回答门槛：当问题涉及多种可能方向时，列出 2-3 个选项供用户选择或补充
